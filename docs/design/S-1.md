# Design doc S-1: Status pipeline (recruiter moves an applicant's stage)

**Story S-1.** As an HR recruiter, I want to move each applicant forward one stage at a time (Applied → Screened → Interview → Offer), or to Rejected, with any other move refused, so that the pipeline shows each applicant's true stage and I don't rebuild stage data by hand for reports and audits.

## 1. Problem
Recruiters can't trust the stage data in their current tools. One rebuilt a weekly pipeline report by hand because stages were wrong for about a third of candidates (E-5). A director spent about 30 hours cleaning an audit export (E-6). A recruiter keeps a side spreadsheet because the pipeline view doesn't show next steps (E-7). A stage that can only change under fixed rules removes that cleanup.

## 2. Scope
- Create an application for a posting. It starts at Applied. This is a minimal endpoint so applications exist; S-7 later adds accounts and documents.
- Move an application to a new stage. The move is allowed only by the transition table in Rules.
- Show the pipeline for a posting: every application, grouped by stage.

## 3. Non-goals
- No authentication or role checks. Any caller may move a stage (A-4; accounts arrive with S-7).
- No applicant-facing view or labels (S-2, Q-1).
- No notifications to anyone, including the applicant's manager (S-5, Q-7).
- No Withdrawn stage (S-10, Q-4).
- No persistence across restarts. Data is held in memory for this milestone; S-6 adds storage.
- No automatic moves. Only an explicit request changes a stage.

## 4. Interface
Python package `jobsboard`. The HTTP app is `jobsboard.api:app` (FastAPI).

Domain, `jobsboard.pipeline`:
- `class Stage(str, Enum)`: `APPLIED="Applied"`, `SCREENED="Screened"`, `INTERVIEW="Interview"`, `OFFER="Offer"`, `REJECTED="Rejected"`.
- `def allowed_next(stage: Stage) -> frozenset[Stage]`. Never raises.
- `def move_stage(store: ApplicationStore, application_id: str, to_stage: Stage) -> Application`. Raises `ApplicationNotFound(application_id)` or `InvalidTransition(from_stage: Stage, to_stage: Stage)`.
- `class ApplicationStore`: `create(posting_id: str, applicant_id: str) -> Application`, `get(application_id: str) -> Application` (raises `ApplicationNotFound`), `list_for_posting(posting_id: str) -> list[Application]`.

HTTP:

| Method and path | Body | Success | Errors |
| --- | --- | --- | --- |
| `POST /postings/{posting_id}/applications` | `{"applicant_id": str}` | 201, Application JSON | 422 if `applicant_id` is missing or empty |
| `POST /applications/{application_id}/stage` | `{"to_stage": str}` | 200, Application JSON | 404 `{"detail": {"error": "application_not_found", "application_id": ...}}`; 409 `{"detail": {"error": "invalid_transition", "from_stage": ..., "to_stage": ...}}`; 422 if `to_stage` is not one of the five stage names |
| `GET /postings/{posting_id}/pipeline` | none | 200 `{"posting_id": str, "stages": {"Applied": [str], "Screened": [str], "Interview": [str], "Offer": [str], "Rejected": [str]}}`, lists of application IDs in creation order | none; an unknown posting returns five empty lists |

Application JSON: `{"application_id": str, "posting_id": str, "applicant_id": str, "stage": str}`.

## 5. Data
- `application_id: str`, assigned by the server, unique, never reused, and never changes.
- `posting_id: str`, non-empty, set at creation, never changes.
- `applicant_id: str`, non-empty, set at creation, never changes.
- `stage: Stage`, exactly one of the five values; `Applied` at creation.

## 6. Rules
- **R1 (transition table).** `allowed_next` is: Applied → {Screened, Rejected}; Screened → {Interview, Rejected}; Interview → {Offer, Rejected}; Rejected → {} (A-2, A-3). Moves out of Offer are covered by open question OQ-1.
- **R2 (precondition).** A move succeeds only if `to_stage ∈ allowed_next(current stage)`. Otherwise it returns 409 and names both stages.
- **R3 (postcondition).** After a successful move, `GET` on the pipeline lists the application under `to_stage`.
- **R4 (refused move changes nothing).** After a 404, 409, or 422 response, the pipeline response is identical to the one before the request.
- **R5 (invariant).** For every posting, each of its applications appears in exactly one stage list, and the lengths of the five lists add up to the number of applications created for that posting.

## 7. Edge cases
- Moving to the current stage (Screened → Screened). It is not in the table, so it returns 409.
- A backward move (Interview → Screened). Returns 409.
- A stage name in the wrong case or not in the list (`"screened"`, `"Hired"`). Returns 422, not 409.
- An unknown `application_id`. Returns 404 and changes nothing.
- A posting with no applications. The pipeline shows five empty lists, with every key present.

## 8. Decisions and open questions
**Decisions**
- D1. Stage names are exactly the five strings in Interface, and the match is case-sensitive (A-1).
- D2. Moves follow R1: forward one stage, or to Rejected from Applied, Screened, or Interview (A-2).
- D3. Rejected is final (A-3).
- D4. Storage is an in-memory `ApplicationStore`, rebuilt empty on each start, for this milestone.
- D5. A refused move returns 409 with `from_stage` and `to_stage`. An unknown stage name returns 422.

**Open questions**
- OQ-1 (Q-3). When an offer is declined or rescinded, where does the application go? Do not build anything that depends on this. Stop and ask.
- OQ-2 (Q-4). Is Withdrawn a separate final stage, and who may set it? Do not build anything that depends on this. Stop and ask.
- OQ-3 (Q-1). Which stage labels does an applicant see? Do not build anything that depends on this. Stop and ask.
